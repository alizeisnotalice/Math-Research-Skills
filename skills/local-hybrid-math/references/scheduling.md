# 按实际工作量调度

先选择算法和数据布局，再选择设备。减少复杂度、向量化、稀疏表示、避免重复分解/重复读取通常比单纯换设备收益更大。

## 选路顺序

1. **精度**：精确/符号/区间、高精度或真正 float64 需求使用 CPU。float32 可行时才让本机 GPU 竞争，不因“加速”擅自降精度。
2. **粒度**：小矩阵、控制逻辑、分支/稀疏遍历、短计算优先原生 CPU；GPU 需要足够大或足够多的同类运算摊薄调度开销。
3. **数据驻留**：GPU 多步计算只上传一次，尽量最后才取回结果。不要在循环中 `.cpu()`、`Normal`、MAT 文件往返或启动新解释器。
4. **实际总耗时**：比较同一问题、同一精度，包含调用边界/传输。Python 的 warm backend 比较不代表 MATLAB 冷启动桥接的总收益。
5. **并发**：单个 GPU 作业与 CPU 预处理/独立任务形成有界流水线。起步一个 GPU worker，CPU 每个作业固定线程预算；总线程不超可用核数。多进程各开全核 BLAS 会争用资源。
6. **内存与负载**：Apple CPU/GPU 共享内存和带宽。CPU/GPU 同时跑满可能更慢；用实测吞吐、峰值内存和完成时间决定并发，而非追求所有利用率数字最大。

## 自动调度器

`hybrid_math.py` 对同一实际尺寸比较 NumPy CPU、PyTorch CPU 的 1/2/4/8/本机核数线程，以及可用且精度允许的 MPS。每个候选预热一次，取三次实际操作的中位数；GPU 段包含上传和下载。GPU 至少快 10% 才自动选择，避免微小波动引起切换。

校准按解释器、库版本、平台、CPU 核数、运算、形状、类型与 MPS 可用性缓存，最多 100 项、24 小时。显式 CPU 模式只校准 CPU；显式 MPS 模式只校准 GPU。资源负载变化时主动刷新。该缓存影响性能选择，不能代替每次独立的正确性核验。

首次校准会执行多个候选，可能比直接运算慢。重复批次放在同一 Python 进程中，复用模块、缓存和 GPU 数组；短任务直接调用原生 CPU 更合适。当前通用接口是单次数组任务，复杂多步算法应写项目专用脚本；`benchmark_residency.py` 提供已执行的多步传播样例。

## CPU 与 GPU 的分工

CPU：符号/精确推导、条件检查、输入生成与清洗、稀疏/离散搜索、批量调度、float64 对照与后处理。

GPU：适合的稠密矩阵、向量化概率模拟、数组函数与 FFT，多步保持数组在设备上。GPU 执行时，CPU 只重叠确实独立的工作，避免双方争用同一大块内存。

CPU/GPU 重叠、随机模拟或抽样核验都不产生严格证明。报告抽查了多少元素/样本；不得把抽查写成全数组验证。
