# 支撑包结构与一致性验收

## 结构示例（以题目要求为准）

```text
支撑材料/
  result.xlsx                 # 使用题目指定名称，不一定叫此名
  AI使用说明.pdf
  复现说明.md
  data/raw/                   # 必需且获准提交的原始输入
  data/processed/
  src/
  configs/
  results/                    # 指标、图、必要日志
  environment/                # 依赖/锁文件，不是整个虚拟环境
  paper/                      # 需要提供时：对应源码和资源
  manifest.json               # 如采用文件哈希清单
```

## manifest 设计

每个文件记录规范化相对路径、字节数与 SHA-256；同一套筛选规则用于清单、打包和验收。文件路径唯一，拒绝绝对路径和 `..` 穿越；符号链接不得隐式引入包外内容。

manifest 排除自身。输出 ZIP 在载荷目录外，不能包含自身；外部 PDF/ZIP 的交付哈希也不写回包内引发循环。如果已有官方 manifest 格式，沿用其格式而非强制替换。

CRC 能发现归档损坏，SHA-256 能核对预期字节；二者都不能证明算法正确或数据来源真实。

## 先确定本轮交付约定

将要求列为参数：外层文件、归档格式、各格式大小上限、成员前置顺序、禁止包含的材料、是否需要论文源码和全部代码附录。后来的明确要求优先于旧清单，例如追加 RAR 后应重新核对外层文件数，不能沿用此前“只有 PDF 与 ZIP”的判断。文件名和页数也以本轮要求为准。

大小按实际字节检查；MB 与 MiB 不相同。只有“20M”等模糊说法且无其他依据时，采用两者中较严的十进制上限并说明口径，避免贴边压缩。需要多种格式时分别验收，不能用 ZIP 的大小代表 RAR。压缩工具、虚拟环境、编译缓存、临时图和重复嵌套的旧归档不随载荷提交。

用户排除题干或原始附件时，从提交副本移除对应项目，并检查代码是否依赖其中必要输入；可保留获准提交的有效输入及空白结果模板。若不可缺少的输入也被排除，应说明复现时由读者提供的位置，不能偷偷放回原文件或声称完全自包含。工作目录中的原始证据保留不动。

## 去重必须检查依赖

先按哈希发现候选，再逐项查用途、读写入口及题目要求。空白结果模板可能内容相同但对应不同问题；不同配置的导出文件可能恰好相同但仍被各自路径读取。日志也可能内容相同但代表不同运行来源。保留这些必要的角色与溯源关系，不把“全部哈希唯一”当作验收目标。

CSV、NPZ、MAT 或工作簿不能只因数值看起来相同就互换。核对精度、形状、单位、字段、元数据和读取方式；MAT 文件中附带的模型模式或参数可能无法从 CSV 恢复。删除计算缓存前还要检查恢复逻辑：有些脚本只看摘要 JSON 是否存在便跳过求解，删除 NPZ 而保留摘要会造成无法重建。需要验证时使用独立的空输出目录或已支持的强制重建入口，且必须已有相应计算授权。

用户要求 AI 使用说明仅留 PDF 时，可以移除提交副本中的 Word 版，并同步清单；先确认 PDF 包含应保留的全部内容。对其他文件，只有确认不再被读取、没有独立证据用途且不属于题目要求，才从提交副本删除。

若选择一份实体文件加路径映射，应同时检查恢复器、校验器、重打包器及说明文档是否支持该映射。已有验证器可能要求别名表为空；只添加映射表而不修改读取逻辑会制造断链。优先保留必要的少量重复，或在授权范围内完整修改引用并验证，不能以节省大小为由留下失效入口。

## 顺序、附录与源码一起更新

建立唯一的有序成员列表，供文件索引、附录目录和归档写入共用。文件集合相同不代表顺序满足要求：核对指定的前若干成员、完整顺序和数量；压缩软件界面可能自行按名称排序，应同时核对归档实际成员顺序。

目录使用包内完整相对路径，从解压根目录逐一确认存在、大小写一致、唯一且无越界。移动或删除文件后，同步所有实际使用的生成器、读者、验证器、源码登记、哈希及当前复现说明。历史日志可以保留原路径，但应注明其历史身份并提供映射，不能伪造为当前运行；无需把每次完整旧清单递归塞进新清单。

若用户要求全部数值代码全文入附录，逐个对照实际程序文件及辅助程序：路径、行数、行范围、源哈希和编译输入均须一致。检查列表环境是否只显示旧行数或遗漏新文件；通过隔离编译的 `.fls` 确认读取本次源码。压缩附录篇幅应调整排版，不能擅自删代码。需要修改页码或其他版式时按 `$math-modeling-paper` 的阶段验收流程进行。

## 复现说明至少回答

- 哪个目录执行哪个入口，输入和输出在哪里，输出是否会覆盖已有文件。
- 实际测试的系统、语言版本、依赖与必要许可证；可用兼容替代及尚未验证的限制。
- 参数/种子/求解容差从哪里读，预计资源需求（仅在有依据时给出）。
- 哪条命令只是历史重算，哪条会重新求解、访问网络或运行正式测试。
- 验收依据：精确哈希、数值容差、约束残差或统计指标。跨平台 PDF 二进制不同不必然失败，应核对内容与版式。

## 封包顺序

1. 完成已授权的数据和源文件更新，按既有授权及本轮范围重建受影响的导出结果或文档；不能把封包自动扩大为重新求解模型。
2. 核对结果 Excel、论文图表与必要附录；编译 AI 使用 PDF，并验证内容真实。
3. 检查原始证据未改，清理提交副本中的缓存和无关材料；不要删除私人源目录。
4. 进行匿名与隐私检查，记录未覆盖的格式和需人工查看的图片。
5. 冻结载荷，生成内部清单，在外部新路径按约定顺序生成归档；不覆盖此前交付。
6. 检查归档完整性、成员集合与顺序、每个载荷字节哈希和必需文件；在临时目录做安全解压/复现检查。允许归档内实际解出的文件参与验证，不从旧工作目录借用同名文件。
7. 在包外记录最终 PDF 和各归档的大小与哈希、对应版本、通过/失败/未做的检查及人工待办。

RAR 应由支持写入 RAR 的真实工具生成，不能将 ZIP 改扩展名。核对文件签名、工具的完整性测试，并实际解压。ZIP 与 RAR 使用同一冻结载荷，逐成员比较路径、字节哈希及规定顺序；压缩后字节和大小不同是正常现象。无法生成某格式时如实记录，不交付冒名文件。

封包后不再修改目录内文件。若发现须更新清单、代码或说明，重新冻结并生成所有格式，再执行受影响的检查；不得只重做 ZIP 而留下旧 RAR。论文源输入全部哈希未变时，可以引用已通过的编译验收，不必为仅改包外说明反复重排论文。

## 不应混淆的状态

“材料齐全”不等于“正式数据已补齐”；“能运行”不等于“结果正确”；“字节一致”不等于“来源可信”；“机器检查通过”不等于“参赛队已审核或已提交”。这些状态须分别陈述。
